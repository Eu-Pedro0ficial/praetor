== Crosscutting Concepts

=== Domain-Driven Terminology

The system must use explicit domain terminology rather than overloaded words such as “chat” or “agent memory.” Important concepts include Change, Change Surface, Evidence, Policy, Invariant, Approval, Exception, Memory Record, Memory Candidate, Context Pack, Repository Model, Run, Actor and Provider Capability.

=== Source Change Provenance

For every consequential execution, the system should be able to answer:

* who initiated it;
* what command/workflow step ran;
* which software/workflow/spec/policy versions were used;
* which source commit and memory snapshot were inputs;
* which provider/model and role were used;
* what artifacts and patch were produced;
* which checks passed/failed;
* who approved or rejected it;
* why an exception was granted;
* what durable memory/policy candidates resulted.

Hash/fingerprint candidates include prompt/spec hash, workflow hash, policy hash, model identifier, input commit SHA, output artifact SHA and memory snapshot SHA.

=== Audit Model

Audit is append-oriented. Correction is represented by a later event, not deletion of history. Exact cryptographic immutability is DEFERRED, but the model must permit signed commits/event signatures later.

M1.1 moves active audit authority from global XDG DATA JSONL into the one
per-Project SQLite adapter through the explicit idempotent ADR-038 migration.
Audit records governed artifact references and bounded execution provenance,
not raw provider conversations/streams, arbitrary prompts, credentials,
secrets, or unbounded repository bodies.

=== M1.1 Durable Authority and Local Persistence

Durable Change identity is `(ProjectId, ChangeId)`. Artifacts use opaque
generated identities independent from content digests, immutable versions and
relations, append-only supersession, and versioned Change bindings. The exact
WorkflowSnapshot bytes and digest remain authoritative for the lifetime of the
Change; recovery never substitutes the current workflow.

Logical ChangeStore, ArtifactStore, and AuditLedger responsibilities share one
per-Project SQLite transaction boundary under XDG DATA. ExpectedRevision and a
scoped OperationId/RequestDigest prevent stale or changed retries. External
effects remain sagas outside database transactions; canonical Git mutation adds
a short XDG STATE OS lock and exact PRE/POST proof. The exclusion interval
covers POST proof and its short terminal authority commit. Recovery is
explicit, audited, and orthogonal to ChangeState.

=== Architecture Decision Closure

A decision marked DEFERRED or BENCHMARK/SPIKE REQUIRED MUST NOT be silently resolved by an implementation task or AI agent.

When a milestone reaches the trigger for such a decision:

. dependent implementation must stop;
. the required spike/benchmark/research must be performed;
. an ADR or explicit architecture decision must be produced;
. human approval is required;
. only then may implementation continue.

An implementation convenience is NOT an architecture decision.

=== M1.2 Repository Knowledge, Freshness, and Advisory Risk

ADR-039 separates source evidence, immutable RepositoryModel snapshots, and a
rebuildable per-Project XDG CACHE projection. A composite build key covers the
source fingerprint, model schema, analyzer set, and analysis configuration.
Freshness is `CURRENT`, `STALE`, or `UNKNOWN`; missing or corrupt evidence is
never current. Untracked entry presence/path identity participates through
sorted status-name evidence, while excluded untracked bytes do not. Exclusion
always creates a KnowledgeGap.

Assertions are observed, derived, or inferred. Confidence belongs only to
inference; provenance and gaps remain first-class. Bounded historical facts may
support ownership, co-change context, and history concentration, but M1.2 does
not perform regression analysis, DiffRisk, outcome learning, or failure
prediction.

ADR-040 makes ImpactReport an immutable Change-owned artifact while the model
cache remains disposable. Expected, possible, protected, and uncertain impact
is evidence for planning; ApprovedScope remains the independent write
authority. Risk is advisory. `LOW < MODERATE < HIGH`, while `INDETERMINATE` is
an unordered epistemic result with no automatic approval, rejection, or policy
effect.

=== Provider Context Materialization

Change authorization and provider context materialization are separate.
ApprovedScope answers where a complete Git-derived patch may write.
Materialization answers which bounded information is serialized for an
individual provider request. Repository-wide authorization therefore remains a
compact capability and does not cause whole-repository prompt expansion.

The implementation request retains information the provider cannot safely
reconstruct from source: Change intent, workspace/source identity, write
authority, protected paths, governance, and bounded current advisory impact.
It omits eager source bodies, the complete SourceSnapshot inventory, and the
full RepositoryModel because the provider can inspect the isolated
ProposalWorkspace. Exact adapter-side component accounting is appended to
provider lifecycle audit metadata without persisting request content. Provider
usage remains a separate authoritative report because bytes and tokens are
different measures.

=== Memory Architecture

==== Scopes

* **Session Memory** — ephemeral execution scratch/context; not durable truth.
* **Change Memory** — requirements, impact, decisions, failed approaches, review findings and artifacts for one Change.
* **Project Memory** — durable knowledge about architecture, domain, conventions, dependencies, integrations, risks, testing and regressions.
* **Organization Memory** — validated cross-project policy and engineering knowledge.
* **Developer Memory** — optional personal interaction preferences only; must not silently become project truth.

==== Memory Types

At minimum the model must be able to distinguish: Fact, Decision, Policy, Constraint, Convention, Observation, Hypothesis, Incident, Regression, Workaround, Debt, Risk, Ownership, Dependency, Integration, DomainKnowledge, Glossary, Runbook and Exception.

==== Lifecycle

Candidate lifecycle states include PROPOSED, VALIDATED, ACTIVE, STALE, DEPRECATED, DISPUTED, REJECTED and SUPERSEDED. A dedicated state such as NEEDS_REVALIDATION may be used when evidence fingerprints changed but invalidity is not yet proven.

==== Provenance and Validity

A memory record may reference file, symbol, source commit, hash/fingerprint, originating Change, Run, actor, validation mechanism and approval. Facts derived from mutable code should be invalidatable when their evidence changes. Historical regressions may remain permanently useful; policies/decisions follow their own version/supersession lifecycle.

==== Canonical vs Query vs AI Projection

The architecture deliberately separates three representations:

. **Canonical Git representation** — merge-friendly, reviewable durable records. The exact serialization format remains BENCHMARK REQUIRED until a benchmark and human-approved ADR are complete.
. **Local query projection** — likely SQLite + FTS for fast deterministic retrieval and indexes.
. **AI/context projection** — Markdown/compact/provider-optimized Context Packs selected for the current task.

No single file format is expected to optimize all three purposes.

==== Retrieval Strategy

Retrieval should be structure-first rather than embeddings-first:

. path and symbol relations;
. domain/component relations;
. dependency closure;
. tags and change history;
. full-text search;
. optional semantic retrieval;
. optional reranking;
. final token/context budget assembly.

Long-term memory is a retrievable knowledge system, not accumulated prompt text.

==== Context Packs

A provider receives only task-relevant knowledge. A Context Pack can include affected components, relevant active memory, ADRs, regressions, policies, known gaps and a bounded repository view. The Context Pack itself is auditable and can be fingerprinted.

==== Memory Conflict

The Memory Engine should distinguish textual merge conflict from knowledge conflict. Candidate categories include semantic contradiction, duplicate assertion, supersession, stale evidence and scope conflict. Human resolution may be required for authoritative conflicts.

=== Security and Data Governance

Memory can contain architecture, vulnerabilities, internal endpoints, service names, incidents, code fragments and other sensitive context. Therefore the system requires a path toward:

* secret detection before durable memory;
* PII detection/redaction where appropriate;
* data classification;
* provider allow/deny constraints based on classification;
* access control;
* retention policy;
* audit;
* encryption strategy;
* future organization/tenant isolation.

Provider trust levels are:

* LOCAL
* ENTERPRISE
* EXTERNAL_APPROVED
* EXTERNAL_RESTRICTED
* FORBIDDEN

Data classification is:

* PUBLIC
* INTERNAL
* CONFIDENTIAL
* RESTRICTED

The router must not send context to a provider that violates the data policy, even if that provider is otherwise technically capable.

Configuration precedence is conceptually:

built-in defaults < user configuration < project configuration < workflow configuration < Change-specific configuration

However, configuration precedence does not override governance authority. A lower-level configuration cannot weaken a higher-authority non-overridable policy.

=== Presentation Boundary

M0.9 presentation preferences are a separate user-local rendering concern,
not another layer in governed configuration precedence. Sidebar visibility,
section visibility, and bounded terminal colors cannot affect Project or
Change identity, provider execution, verification, evidence, policy, audit,
canonical integration, or source-state digests. Terminal dimensions may
temporarily suppress presentation but never rewrite stored preference.

Dynamic terminal values are treated as untrusted presentation input: invalid
UTF-8 and control characters are neutralized, display width is measured by
grapheme clusters, and ANSI sequences originate only from a fixed
Praetor-owned palette when the output terminal supports color.

Development debug transcripts are separate from durable audit authority. They
are build-tagged, user-local XDG STATE diagnostics with private permissions,
finite command/session bounds, control neutralization, and best-effort
redaction for common credentials. They retain logical shell interaction only,
never authorize provider raw-stream retention, and remain sensitive diagnostic
artifacts rather than canonical Project records.

=== Role-Based Authority

A possible configurable authority model is:

* Developer — propose memory/change;
* Senior — validate selected conventions;
* Architect — approve architecture decisions;
* Security — approve security policy/exceptions;
* Administrator — manage providers and organization controls.

These exact role names are not hard-coded domain requirements; the requirement is configurable authority over sensitive transitions.

=== Composition Root and Dependency Assembly

Praetor uses an explicit composition root at the process boundary. Runtime dependencies are assembled explicitly and constructor-based, and the container remains a typed assembly mechanism rather than a service locator. Domain and application components must not depend on the container itself, and global mutable registries are explicitly forbidden.

The composition root must contain only the concrete dependencies required for the current implementation surface. A wider dependency graph belongs to a later milestone and must not be introduced prematurely.

=== Coding Standards for the Runtime

The Go implementation follows SOLID, KISS, YAGNI and DRY while avoiding ceremonial abstraction. Identifiers must prefer complete, meaningful words. Single-letter or unnecessary abbreviations such as `c` for `context` are not accepted simply for brevity.

Packages should communicate architectural responsibility. Domain packages cannot depend on concrete external providers. Adapters may depend inward on ports/domain contracts, never the reverse.

=== Observability

Observability must distinguish:

* workflow execution events;
* agent/provider calls;
* deterministic validation runs;
* sandbox operations;
* policy decisions;
* memory retrieval/promotion/invalidation;
* human approvals and exceptions.

Telemetry must not leak source, secrets, prompts or memory beyond configured data policy.

=== Error Handling

Failures are explicit domain outcomes when meaningful. Provider timeout, invalid structured output, sandbox failure, analyzer failure and policy violation are different categories and should not collapse into generic “agent failed.” Retry policy must be role/tool aware and never repeat consequential operations without idempotency safeguards.

M1.1 additionally distinguishes stale revision, bounded busy/conflict,
incomplete operation, uncertain external effect, source divergence, artifact
corruption/missing data, and incompatible store. Attach and inspection diagnose
these conditions but never repair or advance authority implicitly.
