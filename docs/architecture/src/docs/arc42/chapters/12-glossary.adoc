== Glossary

[cols="1,3",options="header"]
|===
|Term |Meaning
|Accepted Change |A proposed code modification that passed required validation/approval and is allowed to affect canonical source state.
|Adapter |Concrete integration implementing a core port for an external technology/provider.
|Agent |Role-scoped AI executor. An agent is not an authority and is not synonymous with a provider.
|Agent Router |Component that maps role requirements and governance constraints to a compatible provider/model adapter.
|Approval |Explicit authorization from an actor with the required authority for a state transition or exception.
|Audit Ledger |Append-oriented event history describing commands, runs, artifacts, decisions, actors and hashes.
|Canonical Memory |Durable accepted memory records representing project/organization engineering knowledge.
|Change |Primary auditable work aggregate representing one requested software evolution/fix.
|Change Surface |Expected, possible, protected and actual files/symbols/modules affected by a Change.
|Context Pack |Task-scoped projection of repository/memory/policy knowledge assembled for one AI role invocation.
|Developer Sovereignty |Principle that the engineering process and authorized humans retain final authority over consequential actions.
|Evidence |Structured result supporting a claim or state transition: tests, scans, diffs, analysis, approvals, etc.
|Institutional Engineering Memory |Durable project/organization knowledge independent from an individual developer or AI provider.
|Knowledge Gap |Explicitly represented unknown or insufficiently supported area of project understanding.
|Memory Candidate |Proposed knowledge record that has not yet become canonical memory.
|Memory Invalidation |Process of identifying previously valid memory whose supporting source/evidence changed.
|Memory Snapshot |Reference/fingerprint identifying the memory state used for an execution.
|Minimum Necessary Change |Optimization principle minimizing modification surface while satisfying correctness and constraints.
|Policy |Executable or governable engineering invariant that can allow, deny, require review/approval, or mark advisory findings.
|Port |Core-owned interface describing a capability required from external systems.
|Project Registry |Mapping between project identity, source repository, memory repository and configuration.
|Provider |External or local AI service/runtime supplying model execution.
|Provider Trust Level |Governance classification restricting which data can be sent to a provider.
|Provenance |Evidence of origin: actor, command, source commit, memory snapshot, model, input/output and hashes.
|Repository Archaeology |Initial/incremental discovery process that reconstructs structure, dependencies, testing, integrations and legacy constraints.
|Repository Model |Structured representation of a source repository used for impact, retrieval and validation.
|Role |Logical agent responsibility such as Planner, Implementer or Security Reviewer.
|Run |One execution attempt of a workflow step/tool/agent.
|Sandbox |Isolated environment where proposed source modifications execute before acceptance.
|Software Change Provenance |Ability to reconstruct why/how/by-whom/with-what-context a code change was produced and accepted.
|State Machine |Explicit allowed progression of a Change rather than agent-controlled free-form progression.
|Workflow |Versioned engineering process defining stages, contracts, gates and allowed transitions.
|===
