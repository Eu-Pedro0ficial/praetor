==== CLI / Developer Interface

Responsibilities:

* project initialization and attachment;
* change creation and inspection;
* explicit execution of workflow steps;
* approval/rejection/exception commands;
* inspection of evidence, diffs, policy violations and memory;
* provider/project configuration and presentation preferences;
* status and audit navigation.

The developer interface is a persistent, retained-context shell. A
Praetor-owned hierarchical command tree scopes commands by mode and is the
single source for dispatch, help, descriptions, usage, completion, and
contextual `?`. The session owns a separate presentation-navigation mode
stack; entering or leaving a mode does not change Project identity, Change
state, or workflow state.

The readline adapter owns terminal key handling, history, buffer/cursor
redisplay, and completion rendering only. The CLI is an inbound adapter. It
must not contain domain logic that cannot also be invoked by another future
adapter such as an API, IDE extension, or desktop UI.

The M0.9 Engineering Console renderer owns only terminal presentation: a
minimal header/footer, a width-adaptive command surface, and an optional right
sidebar. Both the sidebar and the `status` command project the same
presentation-neutral session status snapshot. A narrow user-local preference
service persists layout and a bounded color vocabulary through the explicit
composition root; neither preferences nor terminal state enter the domain or
application model.

Interactive history retains logical rows and reflows them by Unicode grapheme
display width for the current viewport. Vertical viewport navigation therefore
reaches long output after narrow rendering or resize; redirected output bypasses
interactive reflow. A build-tagged development transcript adapter may observe
the shell command/logical-output boundary. It persists bounded, sanitized
diagnostics under XDG STATE and is absent from ordinary/release executable
composition; command handlers, application services, provider adapters, and
domain code do not depend on it.

==== Workflow Engine

The Workflow Engine is the orchestration authority. It evaluates the current Change state, exact bound WorkflowSnapshot, policies, approvals and generated artifacts to determine which operations are allowed. M1.1 retains the original embedded Core V0 YAML bytes, identity, version, schema version, and digest; it never substitutes a current definition or automatically migrates an in-flight Change.

It MUST NOT encode provider-specific behavior. It coordinates ports such as Agent Execution, Repository, Verification, Memory, Audit and Approval.

==== Change Domain

The Change aggregate preserves intent and state. Candidate concepts include:

* ChangeId
* ChangeType
* ChangeIntent
* ChangeState
* ChangeSurface
* RiskClassification
* Specification
* Plan
* ExecutionAttempt
* VerificationResult
* ReviewResult
* Approval
* Exception
* Postmortem

ADR-033 fixes durable identity as `(ProjectId, ChangeId)` and leaves the
accepted state machine unchanged. M1.1 persistence adds immutable
versioned Artifact records, immutable relations, append-only supersession, and
versioned current bindings. ArtifactId is opaque and independent from payload
digest; every M1.1 artifact belongs to exactly one Project and Change.

==== Durable Change Persistence

M1.1's logical ChangeStore, ArtifactStore, and AuditLedger responsibilities are
backed by one physical per-Project SQLite adapter under XDG DATA. A narrow typed
authority commit atomically checks ExpectedRevision and writes the Change
revision, artifact records/relations/bindings, operation outcome, and audit
events. External effects never run inside that transaction. These components
are implemented; later Specification, review, identity, and retention maturity
remain owned by their roadmap milestones.

Read-only application use cases expose bounded durable Change, workflow,
artifact, audit, and recovery diagnosis without automatically migrating,
repairing, or advancing authority. Approval Port maturity remains M1.4;
M1.1 persists references to existing HumanDecision artifacts only.

==== Specification Engine

Transforms normalized intent and repository context into an explicit behavioral/technical specification or validates a human-provided spec. It is responsible for specification completeness and traceability, not implementation.

M1.3 plans versioned Specification Packs and end-to-end requirement -> spec ->
change -> evidence -> policy traceability. `engineering/specs/` is a candidate
future governed-source location only; its format, authority, persistence, and
invalidation semantics require the M1.3 decision gate and are not part of the
current runtime.

==== Policy Engine

Evaluates executable engineering invariants. It must support deterministic checks and may use AI-assisted classification only where deterministic evaluation is insufficient. Policy decisions are system decisions with evidence.

Policy families include clean code, testing, architecture, security, dependency management, change surface, backward compatibility, performance, observability, error handling, API contracts and database changes.

The M1.0 implementation is a representation-independent `internal/policy`
domain/application component. A project adapter owns strict Manifest V1 YAML
loading, a severity adapter normalizes tool vocabulary, and the composition
root supplies both with append-oriented audit. The generic engine never invokes
providers, terminal facilities, Git, filesystem operations, or arbitrary
policy-defined commands.

==== Repository Intelligence

Builds immutable Project-scoped RepositoryModel snapshots. ADR-039 binds every
model to the exact source fingerprint, model schema, analyzer set, and analysis
configuration. Assertions distinguish observed, derived, and inferred facts;
only inference has confidence, and missing or excluded knowledge becomes a
structured KnowledgeGap.

The implemented M1.2 graph is bounded to repository/module/file/symbol/test/API,
external-dependency, owner, architecture-element, and unresolved-reference
nodes with explicit relationship types. Initial analyzers are in-process,
read-only, compile-time registered adapters. Bounded history may supply
ownership/co-change repository context but never M4.2 regression prediction or
DiffRisk.

The earlier M0.3 subset remains the source snapshot and ApprovedScope
foundation. M1.2 evolves the same repository boundary with composite tracked
content and untracked status-name fingerprinting, bounded history, language
signals, exact build keys, and a disposable cache; it does not introduce a
competing source authority.

==== Impact Engine

Computes a bounded, explainable blast radius from an exact RepositoryModel and
classifies elements as expected, possible, protected, or uncertain. Traversal
is relation-specific, cycle-safe, evidence-bearing, and produces gaps when a
limit or unavailable relationship prevents a conclusion. ADR-040 keeps these
results separate from ApprovedScope: analysis never grants write authority.

The durable result is an immutable Change-owned ImpactReport in the M1.1
Artifact authority. It embeds an advisory RiskProfile and exact freshness
inputs so it remains inspectable when the derived model cache is absent. A
current workflow may use it only after proving those inputs remain current.
`LOW < MODERATE < HIGH`; `INDETERMINATE` is an unordered statement of
insufficient evidence and has no automatic governance consequence.

M0.3 candidate selection remains deterministic and explicit: developer-supplied
file paths are normalized and verified against the SourceSnapshot tracked
inventory, and exact actual paths remain governed by ApprovedScope. M1.2's
richer inference is implemented as evidence only and does not change that
authority.

==== Agent Router

Selects an AI provider/model adapter based on the role's required capabilities and governance constraints. Routing dimensions include:

* structured-output support;
* context capacity;
* tool capability;
* code/reasoning characteristics;
* execution mode;
* cost/latency policy;
* provider trust level;
* data classification;
* organizational allow/deny policy.

The Agent Router is not part of the M0.5 executable subset. M0.5 performs
exact configuration/session selection only; it does not rank, route, fall
back, or choose providers by capability, trust, classification, cost, or
latency. The executable M0.6 scope introduces a second logical AI role while
reusing the same explicitly selected adapter; this remains manual selection
rather than Agent Router behavior.

==== AI Provider Port and First Adapter

M0.5 introduced the executable AI Provider Port for an implementation attempt
in provider-independent Praetor semantics. M0.6 extends the same port with the
exact read-only `verification-planning` role. A normalized `ExecutionRequest`
is tied to the role-appropriate active or retained ProposalWorkspace and
returns a normalized `ProviderResponse`. The response is untrusted execution
provenance; Git-derived workspace state and actual verification processes are
authoritative.

The composition root explicitly registers exactly one adapter, `codex-cli`,
and resolves the active provider and optional provider-scoped model by exact
name. Adapter and `OpenAI` vendor metadata remain distinct. `codex-cli` shapes
the request, performs bounded local version/capability preflight, invokes
non-interactive `codex exec` in the ProposalWorkspace, bounds and parses JSONL
output, and normalizes failures.
No Codex CLI process types, flags, or event structures cross the port. A
future OpenAI HTTP/SDK adapter is a separate implementation of the same port.

The provider-independent port also accounts for each exact serialized request
before execution. `RequestContextAccounting` retains only bytes, Unicode
characters, included-item counts, omitted-item counts, and truncation state for
a fixed eight-category vocabulary: provider instructions, intent, approved
scope, governance, advisory impact, source context, repository context, and
other. The concrete adapter owns serialization and measurement; neither Codex
prompt text nor provider-specific request types enter domain semantics.

ApprovedScope remains mutation authority. It does not direct eager context
materialization. The implementation adapter sends compact scope constraints
and workspace identity while source content and the tracked inventory remain
available for inspection in the isolated ProposalWorkspace. Only a current
ImpactReport whose intent matches the Change may contribute bounded advisory
navigation entries. This advisory projection never expands ApprovedScope.

==== Sandbox Runtime

Provides isolated execution for agent-proposed source changes. Preferred strategies include isolated worktrees and/or containers. The main working tree is not the default direct write target.

The executable M0.4 subset creates a detached Git worktree outside the
canonical repository at the exact clean `SourceSnapshot` revision. A
canonical-source guard compares `HEAD`, working-tree state, tracked inventory
and source-state digest before and after workspace creation, controlled test
mutation, patch extraction, surface classification and cleanup. The local Git
adapter extracts a deterministic binary-capable patch plus a NUL-delimited
changed-path inventory, and the application service compares the complete path
set with the existing `ApprovedScope`.

This subset is source/workspace isolation, not process, network, container,
VM, credential, or hostile-code containment. M0.4 has no provider or AI
executor. M0.5 adds only the explicitly selected provider adapter operating in
that workspace; it does not turn the worktree into a security sandbox or a
generic command runner. M0.6 adds a separate, allowlisted direct-process
verification adapter; this does not strengthen worktree isolation into
hostile-code containment.

==== Verification Discovery and Planning

The executable M0.6 discovery component derives candidate deterministic checks
from open-ended Repository Intelligence signals such as manifests, build/task
files, test and analysis configuration, CI declarations, toolchain metadata,
and repository scripts. It retains whether knowledge was
repository-declared, deterministically inferred, AI-assisted inferred, or
user/configured. Explicit repository declarations generally outrank AI
inference.

When deterministic signals are ambiguous, the provider-independent AI port
may execute the exact `verification-planning` role. Every invocation has a
fresh ephemeral context and `ExecutionAttemptId` distinct from
`implementation`; the `codex-cli` adapter selects its advertised read-only
sandbox, while before/after patch and canonical-source checks fail closed on
mutation. It produces structured `VerificationCandidate` values only; it is
not the M1.4 Reviewer or Approver and cannot create deterministic evidence.

The planner/candidate normalizer constructs a non-empty structured
`VerificationPlan`. The minimum V0 rule gate validates each required
`VerificationStep` for provenance, a small admitted direct-process template,
executable resolution outside governed source, bounded argument vectors,
ProposalWorkspace-only working-directory scope, environment exposure,
timeout/cancellation, and output limits. AI-produced arbitrary shell text is
never passed to a shell as executable authority.

==== Verification Engine

Coordinates sequential structured validators and emits normalized evidence.
Core V0 infers `go test ./...`, reads recognized `package.json` scripts and
Makefile targets, and keeps additional bounded evidence available to the
planner. Admitted build, test, lint, typecheck, repository-check, and
patch-integrity steps are represented independently from language branches.
Only actual process and integrity results can prove deterministic outcomes;
provider completion and planning/semantic findings remain separate
provenance. An empty plan, missing tool, non-zero exit, timeout, cancellation,
execution error, or integrity failure cannot pass.

M1.5 later broadens this provider/tool-independent evidence architecture with
advanced quality/security adapters and a Policy Engine-composed Quality Gate.
It may reuse approved existing infrastructure or open-source/local fallbacks,
but retains availability, applicability, source and materially different
assurance rather than treating all tools as equivalent.

==== Review Engine

Coordinates independent AI review roles and deterministic evidence summaries. It must record disagreements rather than flattening them into a false consensus.

The independent Review Engine is a target M1.4 component. The current local
human disposition gate and M0.6 verification planner are executable subsets of
different responsibilities and do not satisfy maker-checker review.

==== Cross-Cutting Inspection, Presentation, and Operability

Explainable source-linked views are supporting read models of M1.1 artifact
inspection, M1.3 Specification/Change traceability, and M2.1 memory retrieval.
They remain subordinate to authoritative requirements, artifacts, evidence,
policies, and decisions; freshness, provenance, gaps, and rebuild behavior are
explicit.

Human-facing governance state, blockers, consequences, rework, exceptions,
and available actions are acceptance concerns of M1.4 and other owning
milestones. The M0.9 presentation boundary may render and invoke them but
cannot infer authority, alter policy, manufacture evidence, or become
canonical state.

Recovery and local concurrency remain with M1.1 durability. M1.5 owns
cancellation, bounded resources, process/network/credential boundaries, and
diagnostics only for its quality/security tool execution. Git worktrees remain
source/workspace isolation, not hostile-code containment. These concerns do
not constitute independent roadmap milestones.

==== Audit Ledger

Receives append-oriented events for commands, runs, bounded governed output
references/provenance, model/provider identity, hashes, state transitions,
approvals, memory promotions, policy outcomes and exceptions. It is logically
separate from Change and Artifact stores while sharing the one M1.1 physical
transactional adapter. It is not canonical artifact storage and excludes raw
provider conversations/streams, arbitrary prompts, credentials, secrets, and
unbounded repository bodies.

==== Approval Gate

The M0.7 application service exposes a terminal-independent Approval Port.
It accepts only explicit `APPROVE` or `REJECT`, requires a validated Change and
coherent retained patch/evidence linkage, reuses proposal/canonical integrity
checks, records bounded `HUMAN_DECISION_RECORDED` provenance, and then invokes
the existing audited workflow transition. The local interactive command
adapter is the sole M0.7 caller. It does not depend on an AI provider, mutate
canonical source, or enter `audit-locked`.

==== Canonical Integration Gate

The M0.8 application service consumes the retained Proposal, passing
EvidenceSet, and exact HumanDecision through a provider-independent application
boundary. `APPROVE` permits only a separate explicit working-tree application;
`REJECT` permits only unchanged-source closure. The Git adapter checks the
exact retained patch and canonical base, runs `git apply --check`, records a
durable start before mutation, and applies patch bytes through stdin using
default whole-patch behavior. It then proves exact canonical diff and changed
paths, unchanged HEAD and index, and the retained patch digest. Completion
audit precedes `approved -> audit-locked`; rejection closure audit precedes
`rejected -> audit-locked`. The component has no commit, push, merge, branch,
PR, remote-SCM, or provider-execution capability.

==== Project Registry

Associates a project identity with its source repository, memory repository and local configuration without requiring the source repository itself to contain a Git submodule or vendor-specific metadata.
