=== Workflow and Command Model

The executable is named `praetor`. Running it starts the interactive developer
shell, which retains the active Project context for the session. Plain commands
are organized in hierarchical contextual modes. One Praetor-owned command tree
drives dispatch, help, usage, descriptions, completion, contextual `?`, and
mode-valid discovery. Readline remains a presentation adapter only.

==== Current Command Hierarchy

[source,text]
----
status
analysis [model|impact|report|inspect ...]
change [new|list|show|select|artifacts|history|diagnose|recover|content|
        isolate|implement|patch|verify|approve|reject|apply|close|discard ...]
policy [show|list|evaluate|exception ...]
provider [list|show|select|model ...]
configure project
configure layout show
configure layout sidebar [show|identity|context|provider|status] <on|off>
configure layout color [accent|border|background|text] <color>
configure layout reset
help [<command> [<child> ...]]
?
end
exit
----

`analysis`, `change`, `provider`, and `configure` enter child modes when
invoked without a child. The same implemented child may be invoked directly
from its parent;
`analysis impact ...` and `analysis` followed by `impact ...` resolve the same
handler. `end` returns exactly one contextual level. `exit` is available only
at root. The `configure project` mode currently has navigation/help only and
does not invent Project configuration persistence.

At any point during interactive editing, `?` resolves contextual commands or
options without executing or clearing the partially typed input. The readline
adapter redisplays the preserved buffer and cursor; semantic help remains
terminal-independent in the command registry.

Future Project, Memory, Audit, and SCM families remain roadmap capabilities and
are not registered as empty placeholder commands. M1.0 registers `policy show`,
`policy list`, `policy evaluate`, and `policy exception` through the same
immutable tree. Direct and contextual forms share dispatch, help, completion,
and contextual `?`. Successful verification records policy after the existing
transition to `validated`; policy itself performs no transition. Positive
approval requires a coherent retained decision, while rejection remains
available.

==== UX4 CLI Option Review

The immutable registry exposes exactly four GNU-style named options, all owned
by Change Surface commands:

[cols="1,2,2,3",options="header"]
|===
|Option |Commands |Default/requirement |Semantics
|`--expected <path>...`
|`analysis impact`, `analysis report`, `change isolate`
|Optional for isolation; analysis requires at least expected or possible
|Strongly expected exact tracked paths. `.` selects repository-wide mode.
|`--possible <path>...`
|`analysis impact`, `analysis report`, `change isolate`
|Optional for isolation; analysis requires at least expected or possible
|Additional exact tracked paths. `.` selects repository-wide mode.
|`--protected <path>...`
|`analysis impact`, `analysis report`, `change isolate`
|Optional
|Forbidden tracked path or subtree in either authorization mode.
|`--actual <path>...`
|`analysis impact` only
|Required
|Complete caller-supplied surface for the M0.3 proof command; runtime patch
validation obtains this set from Git instead.
|===

No other user-facing command has a named option. The positional inputs were
reviewed as part of UX4:

* `change show`, `artifacts`, `history` and `diagnose` infer the selected
  Change when their ChangeId is omitted;
* `change content` infers the selected Change but retains required ArtifactId;
* `change approve` and `reject` keep rationale optional;
* provider model omission continues to mean the provider default; explicit
  provider/model selection cannot be inferred safely;
* analysis intent, actual proof paths, recovery identity, policy exception
  authority/reason, lifecycle state requests, and layout values remain
  explicit because inference would be ambiguous or would weaken governance;
* read-only commands and navigation have no unnecessary options.

The optional leading `/` compatibility spelling is retained for existing
scripts. Direct child invocation and contextual-mode invocation intentionally
resolve the same registry definition, while `help` and `?` remain distinct
full and contextual discovery actions. These equivalent entry forms add no
authorization semantics and do not justify another alias or scope flag.

UX4 removes the mandatory expected-path prediction only from `change isolate`.
It also permits a possible-only strict surface because the domain already gives
that category a complete deterministic meaning. No aliases or new flags were
added.

==== M0.2 Executable Shell Proof

The current M0.2 runtime exposes only the smallest command paths needed to
prove project attachment and the Change lifecycle:

[source,text]
----
status
change new <change-id> <intent> [<state> ...]
----

`change new` creates the Change in `created`. Optional state arguments request
an ordered sequence of transitions in the same invocation; every state and
edge is validated by the domain aggregate. The command prints the final
identity, Project association, intent and state only after all requested
transitions succeed.

The M0.2 state adapter is intentionally process-local, as permitted by the
milestone. The optional transition sequence is therefore an end-to-end proof
surface, not a durable resume interface. Cross-process Change resume and the
other command families above require later persistence and milestone behavior.

==== M0.3 Executable Shell Proof

M0.3 exposes one explicit file-level proof command under the canonical
high-level analysis family:

[source,text]
----
analysis impact <change-id> <intent> \
  [--expected <path>...] \
  [--possible <path>...] \
  [--protected <path>...] \
  --actual <path>...
----

At least one expected or possible path is required; either category may contain
the sole token `.` to request repository-wide authorization.

The shell resolves and retains the current registered project at startup. The
command creates the process-local M0.2 Change, captures a SourceSnapshot, produces deterministic
ImpactAnalysis from the explicit path input, establishes the resulting
ApprovedScope and validates the complete actual path set. It prints snapshot,
surface, classification and violation details. A protected, unexpected or
invalid path is rejected and reported while the interactive shell remains
active, after the violation is appended to audit history.

The command does not modify source, infer semantic impact, enforce symbols,
create a worktree or produce a patch. `reeflective/readline` v1.3.0 supplies
terminal editing and discovery only; command definitions and behavior remain
Praetor-owned and terminal-independent.

==== M0.4 Executable Proposal Proof

M0.4 extends the existing `change` family:

[source,text]
----
change isolate <change-id> <intent> \
  [--expected <path>...] \
  [--possible <path>...] \
  [--protected <path>...]
change patch
change discard
----

`change isolate` creates and plans the Change, establishes the M0.3
`ApprovedScope`, rejects dirty canonical source, then creates a detached Git
worktree at the captured revision and advances the Change to `isolated`. Its
random temporary path is outside canonical source and is not derived from
`ChangeId`.

With no expected or possible option, `change isolate` records
`repository-wide` authorization rooted at `.`. The equivalent explicit forms are
`--expected .` and `--possible .`. Using both root forms, mixing a root form
with an explicit allowed path, or protecting `.` is rejected before Change
creation. Supplying explicit expected and/or possible paths retains strict
allowlist behavior. Protected paths and tracked subtrees take precedence in
both modes.

`change patch` extracts the actual Git patch and complete changed-path set. A
surface-valid result is retained for later milestones while the Change remains
`isolated`; it is not deterministic evidence validation or human approval. An
empty, protected, unexpected, invalid or mixed forbidden patch is rejected as
a whole, advances the Change to `rejected`, and cleans the worktree.
`change discard` explicitly performs the same rejection and owned-worktree
cleanup.
Session shutdown also rejects and cleans an outstanding proposal.

M0.4 provides only a narrow application callback for isolated-mutation tests.
It does not expose a provider, generic shell runner or AI execution command.
The central command registry remains the single source for help, usage,
completion and dispatch metadata.

==== M0.5 Executable Provider Proof

M0.5 adds one provider-independent workflow command and one infrastructure
selection family:

[source,text]
----
change implement
provider list
provider show
provider select <provider>
provider model <provider-scoped-model>
----

`change implement` consumes the current process-local active proposal created
by `change isolate`. It executes the exactly selected adapter in that
ProposalWorkspace, then delegates to the existing M0.4 patch extraction and
surface classification. It neither repeats isolation nor accepts an arbitrary
working directory. Direct `change implement` and contextual `change` followed
by `implement` resolve the same handler. In Change mode, contextual `?`
includes `implement` without exposing provider credentials or adapter flags.

The `provider` mode lists compile-time registered adapter descriptors, shows
adapter/vendor/model identity separately, and changes the active process-local
provider and optional provider-scoped model through distinct commands.
Selection is exact: an unknown name fails without fallback. `select ?` derives
provider candidates from the registered catalog; models are not remotely
enumerated. It is infrastructure/session configuration, not capability
routing or domain state.
No persistent Project configuration format is introduced.

On provider, guard, empty-patch, or surface failure, the command rejects the
Change and cleans the process-owned proposal according to the current M0.4
ownership semantics. On success, it reports bounded provider provenance and
the Git-derived patch summary; the proposal remains retained and the Change
remains `isolated`.

==== M0.6 Executable Verification Workflow

M0.6 adds direct `change verify` and contextual `verify` commands over the same
centralized handler. The implemented workflow is:

[source,text]
----
surface-valid Proposal + PatchArtifact
  -> language/toolchain-independent repository verification discovery
  -> optional read-only verification-planning AI attempt
  -> provenance-bearing VerificationCandidate values
  -> structured VerificationPlan validation
  -> deterministic Verification Engine execution
  -> normalized EvidenceSet
  -> existing isolated -> validated transition when required evidence passes
  -> M0.7 human decision later
----

The `verification-planning` role uses an execution attempt and fresh context
separate from `implementation`. It may propose what deterministic checks
should run, but cannot mutate source, execute arbitrary shell text, declare a
check passed, review semantic correctness, or approve/reject the Change. The
same explicitly selected provider adapter may serve both roles without adding
automatic routing, fallback, or multi-provider execution.

The M0.6 shell surface remains in ADR-029's single hierarchical metadata tree,
so contextual help, completion, direct invocation, and mode navigation share
the same command definition. Passing deterministic evidence advances only
`isolated -> validated`; failure retains the proposal and leaves the Change
`isolated`.

==== M0.7 Human Approval and Rejection Workflow

M0.7 adds direct `change approve [<rationale>]` and
`change reject [<rationale>]`, plus contextual `approve` and `reject` in
Change mode, through ADR-029's same immutable command tree. Empty input,
contextual help, completion, provider completion, verification success,
timeout, cancellation, and session close never manufacture approval.

Before a decision, the shell prints a bounded summary of Change identity and
state, patch digest/summary and changed paths, plus PASS and
verification/evidence linkage. The Approval Port then requires `validated`,
validates exact retained proposal/evidence linkage, and reuses the proposal
integrity guard for proposal and canonical-source drift.

After all preconditions pass, the service appends
`HUMAN_DECISION_RECORDED`, rechecks integrity, and asks the existing Workflow
Service for `validated -> approved` or `validated -> rejected`. The decision
event therefore precedes the separately appended `CHANGE_TRANSITION`. If the
decision append fails, state remains `validated`. If the decision append
succeeds but the later transition append/state operation fails, the truthful
attempted decision remains in append-oriented history while process-local
state remains unchanged; M0.7 does not claim transactionality.

This workflow is authorization-only. It retains the proposal during the
active session, does not mutate canonical source, and does not automatically
perform `approved/rejected -> audit-locked`.

==== M0.8 Canonical Application and Rejection Closure Workflow

M0.8 adds direct `change apply` and `change close`, plus contextual `apply` and
`close`, through the same ADR-029 command metadata. `apply` requires the exact
retained `APPROVE` chain and remains a separate developer operation. It runs
preflight, durably records start, rechecks before mutation, performs
working-tree-only application, proves the exact result, durably records
completion, and only then requests `approved -> audit-locked`. `close`
requires the exact `REJECT` chain, proves canonical source unchanged, records
closure, and only then requests `rejected -> audit-locked`; it cannot call the
canonical application port.

If mutation occurs before a later failure, the Change remains `approved`, the
caller receives mutation/proof state, session cleanup removes only its owned
workspace, and replay cannot apply the patch again. No automatic execution is
attached to approval, rejection, verification, provider completion, help,
completion, empty input, or session close. Both successful terminal paths use
the existing session-owned workspace cleanup and preserve audit history.

==== M0.9 Presentation Configuration

M0.9 extends the same immutable command tree without adding a parser:

[source,text]
----
configure layout show
configure layout sidebar show|identity|context|provider|status <on|off>
configure layout color accent|border|background|text <color>
configure layout reset
----

Direct paths and their contextual equivalents resolve the same handlers.
Help, contextual `?`, and completion derive from the command metadata and do
not mutate preferences. Each mutating command validates and persists the full
candidate before changing session-visible presentation. These commands cannot
change Project, Change, provider selection, verification, decision, source, or
audit state.

==== M1.1 Durable Workflow

M1.1 binds every Change to the exact embedded, schema-validated Core V0 YAML
WorkflowSnapshot and persists immutable artifacts and current bindings through
one typed ExpectedRevision authority commit. Read-only use cases list/load a
Change, show state/revision/workflow, inspect artifact metadata/relations and
explicit bounded content, show audit history, and diagnose incomplete
operations without migration, repair, or transition side effects. The
implemented commands are `change list`, `show`, `select`, `artifacts`,
`history`, `diagnose`, `content`, and explicit `recover`.

`change select` on an executable in-flight snapshot hydrates the proposal,
Verification/EvidenceSet, PolicyDecision, and HumanDecision projections from
their current durable bindings. It validates their identity, ownership,
digests, schemas, and linkage into temporary projections before publishing the
selected Change and its session caches together. Failed hydration leaves the
previous session selection intact. An unsupported
historical workflow remains selectable for inspection but no command may
advance it.

Consequential operations reserve a Project-unique OperationId and immutable
RequestDigest. The same identity/digest resolves its existing result; a changed
digest or stale ExpectedRevision fails. Canonical Git mutation additionally
uses a durable reservation, short Project OS lock under XDG STATE, and exact
PRE/POST proof. PRE can be explicitly retried but is never automatically
replayed; verified POST may be explicitly finalized; AMBIGUOUS blocks for human
remediation.
For a completed operation, explicit recovery additionally requires its
persisted structured Result to agree with independently verified POST. A
malformed or contradictory Result blocks terminal authority. Without a selected
Change, `change diagnose` requests an explicit ChangeId rather than claiming
Project-wide recovery is clean.

==== M1.2 Implemented Repository Intelligence Workflow

M1.2 extends the existing analysis responsibility. It builds or reuses an
exact current RepositoryModel,
derives bounded explainable impact and advisory risk, and appends an immutable
Change-owned ImpactReport through the existing artifact authority. A stale or
unknown model/report cannot silently drive current planning, and inferred
impact cannot expand ApprovedScope.

The existing ADR-029 command tree provides `analysis model`, `analysis report`,
and `analysis inspect`. They expose exact source/model and ArtifactId
provenance, explanation steps, advisory risk dimensions, and gaps; historical
reports remain inspectable; and cache rebuild stays distinct from durable
artifact mutation. Help, completion, inspection, cache loss, and analyzer
failure cannot authorize source writes or workflow transitions.

==== M1.3 Target Specification and ChangePlan Workflow

M1.3 may add commands only after the Specification/Plan authority gate closes.
The target workflow validates a human-provided or AI-proposed Specification
Pack, obtains any required Plan approval, and binds later proposal, evidence,
policy, review, and human disposition to exact current digests. Mutation of a
governing requirement, Specification, or Plan invalidates dependent authority.

`engineering/specs/` is a candidate future location, not a current command,
directory requirement, persistent format, or accepted source of authority.
Command names and serialization remain intentionally undecided. The required
future linkage is requirement -> spec -> change -> evidence -> policy.

==== Predefined Workloads

The system should support well-defined workflows rather than one universal autonomous loop. Candidate change types may include:

* bug fix;
* small feature;
* refactor;
* dependency upgrade;
* API contract change;
* database migration;
* security fix;
* test-only change;
* documentation-only change;
* legacy characterization / repository archaeology.

Each may select different mandatory gates. A dependency upgrade may require dependency/security verification; a database migration may require explicit approval and migration/backward-compatibility policy; documentation-only work may omit runtime tests.

==== Workflow Versioning

Because workflows influence source changes, exact definition bytes,
identity/version/schema version and SHA-256 digest are authority and execution
provenance. A Change never silently continues under another definition.

Workflow definitions use declarative, versioned YAML with schema validation.
M1.1 admits only the embedded Core V0 definition and performs no automatic
in-flight migration; unsupported old schemas remain inspectable but cannot
advance or fall back. The domain model remains independent from YAML. Project
workflow sources, rebinding, and a custom DSL require later decisions.

==== Pause / Resume

Change state is rebuilt from the exact committed Change revision,
WorkflowSnapshot, artifact bindings, source snapshot, bounded provenance, and
other authorized durable references, never from an LLM chat history.

==== Idempotency

Read-only inspection needs no OperationId. Consequential operations use the
scoped identity/request-digest and recovery semantics in ADR-036 and ADR-037;
unknown external completion never causes automatic repeated execution.

==== Human Interaction Principle

The runtime should make approval cheap when the evidence is good and friction explicit when it is necessary. Human gates are not intended to exist after every model call. Policies determine where humans provide unique governance value.
