=== Policy Model

==== Policy Families

  api-contracts/

----

A policy package contains specification, machine-readable rules, executable checks, evidence schema, severity and exception rules. Policy definitions use declarative, versioned YAML with schema validation.

The domain Policy model remains representation-independent. A custom policy DSL is not selected by default and requires demonstrated need plus an approved ADR.

==== Enforcement Outcomes

* `AUTO` — transition/action may continue automatically after evidence passes.
* `REVIEW` — human review must occur.
* `APPROVAL` — an explicit authorized approval is required before continuation.
* `FORBIDDEN` — action cannot proceed under the current policy; policy change or an explicitly defined higher-order exception mechanism would be required.

==== Policy Is Not Prompt Advice

A rule such as “do not write outside the approved change surface” must be enforced by runtime capabilities/filesystem/sandbox validation where feasible. Prompting may reinforce the rule, but the prompt is not the security boundary.

==== Example Project Policy Profile

[source,yaml]
----
policies:
  clean-code: strict
  architecture: strict
  testing: strict
  backward-compatibility: strict
  security: critical
  performance: advisory
----

This example conveys intent only; the YAML schema remains the authoritative representation.

==== M1.0 Executable Local Policy Model

M1.0 loads `engineering/policies/praetor.yaml` as version-controlled
governance-as-code. The bounded Manifest V1 adapter requires one document with
`schema_version: 1`, bundle identity/version, and policies containing
identity/version, family, description, normalized severity, enforcement
outcome, required evidence kind, non-overridable status, and
exception-candidate permission. Invalid structure, fields, enums, identities,
aliases/anchors, size, nesting, duplicates, symlinks, and executable payloads
fail closed.

Normalized severity is exactly `INFO`, `LOW`, `MEDIUM`, `HIGH`, or `CRITICAL`.
Bundle aggregation independently accumulates denied, review-required, and
approval-required flags while preserving every individual decision.
`REVIEW + APPROVAL` is not a fifth enforcement outcome.

Evaluation follows successful deterministic verification and links the exact
Project, Change, ProposalWorkspace, VerificationAttempt, EvidenceSet, patch digest, source-state
digest, and policy-bundle digest. `AUTO` retains Core V0 human acceptance;
unsatisfied `REVIEW` and `FORBIDDEN` block positive disposition; existing
human `APPROVE` satisfies `APPROVAL`. M1.0 exception candidates are auditable
but cannot be granted or consumed.
