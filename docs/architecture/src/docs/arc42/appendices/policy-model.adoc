=== Policy Model

==== Policy Families

----

----

A policy package contains specification, machine-readable rules, executable checks, evidence schema, severity and exception rules. Policy definitions use declarative, versioned YAML with schema validation.

The domain Policy model remains representation-independent. A custom policy DSL is not selected by default and requires demonstrated need plus an approved ADR.

==== Enforcement Outcomes

* `AUTO` — transition/action may continue automatically after evidence passes.
* `REVIEW` — human review must occur.
* `APPROVAL` — an explicit authorized approval is required before continuation.
* `FORBIDDEN` — action cannot proceed under the current policy; policy change or an explicitly defined higher-order exception mechanism would be required.

==== Policy Is Not Prompt Advice

A rule such as “do not write outside the approved change surface” must be enforced by runtime capabilities/filesystem/sandbox validation where feasible. Prompting may reinforce the rule, but the prompt is not the security boundary.

==== Example Project Policy Profile

[source,yaml]
----
policies:
  clean-code: strict
  architecture: strict
  testing: strict
  backward-compatibility: strict
  security: critical
  performance: advisory
----

This example conveys intent only; the YAML schema remains the authoritative representation.
