=== Security and Threat Model

The runtime intentionally operates on source code, build/test commands, project knowledge and external AI systems. It therefore sits on a sensitive trust boundary and must be designed with an adversarial model rather than assuming well-behaved inputs.

==== Assets

Primary assets include:

* source repositories and uncommitted developer work;
* credentials available on the workstation/CI environment;
* project and organization memory;
* architecture/security incident knowledge;
* prompts/context packs sent to providers;
* provider API credentials;
* issue tracker/SCM access tokens;
* approval identities and authority;
* audit history and hashes;
* generated patches and artifacts.

==== Trust Boundaries

. Engineer workstation -> runtime CLI.
. Runtime -> isolated sandbox/worktree.
. Runtime -> external AI provider.
. Runtime -> local AI provider.
. Runtime -> SCM/issue tracker.
. Runtime -> source Git remote.
. Runtime -> memory Git remote.
. Runtime -> deterministic external tools.
. Project memory -> organization memory promotion.

==== Prompt Injection Posture

The runtime must assume source files, comments, README text, issue descriptions, generated files and memory candidates can contain instructions hostile to the workflow. LLM-facing content is data unless explicitly injected by the trusted workflow/spec/policy renderer. An instruction found inside source content cannot grant tools, expand scope, approve a transition or change provider policy.

==== Least Capability

Each role receives only required tools and paths. A Reviewer may not need source-write capability. A Planner may need read-only repository context. An Implementer may write only within an isolated surface. A Security Reviewer should not automatically receive deployment credentials.

==== Secret Handling

Provider credentials should enter through secure environment/OS credential mechanisms rather than canonical project configuration. Audit should record provider identity but not tokens. Logs and telemetry should redact sensitive payloads by default.

==== Network Policy

A future Sandbox Port should support network modes such as disabled, allowlisted, unrestricted-with-approval or provider-specific gateway. Exact V0 enforcement is TBD.

==== M0.4 Worktree Boundary

The local M0.4 adapter creates random temporary detached worktrees outside the
governed canonical repository and removes only workspaces recorded as owned by
that adapter instance. It passes structured arguments directly to Git, uses
`--` path termination and machine-safe NUL-delimited path parsing, and never
uses raw `ChangeId` text for filesystem placement. A temporary root inside the
canonical repository is rejected before creation.

This protects the developer's canonical source from Praetor's proposal writes;
it does not isolate processes, environment variables, credentials, network,
the host filesystem, containers or virtual machines. No untrusted proposal
program is executed by M0.4.

==== M0.5 Codex CLI Execution Boundary

M0.5 executes the approved `codex-cli` adapter as a local child process. The
adapter passes structured process arguments, selects ephemeral non-interactive
JSONL execution, applies a finite timeout, bounds captured output, and sets the
ProposalWorkspace as both process working directory and Codex working root.
The provider-facing request does not contain canonical `RepositoryRoot`.
Prompt constraints reinforce the ApprovedScope, but only the canonical guard
and Git patch/surface validation enforce Praetor's source boundary.

Codex CLI owns authentication through its normal local mechanism. Praetor does
not inspect or persist tokens, API keys, authorization data, or credential
files. Audit deliberately excludes raw prompts, provider stdout/stderr,
textual summaries, full source, patch bodies, and workspace paths. Normalized
failures do not expose raw provider output.

This does not isolate the provider process from the host filesystem,
environment, credentials, or network and does not make untrusted code safe to
execute. M0.5 neither runs generated project programs nor claims enterprise
trust/data-classification enforcement. M3.0 owns provider trust and data
routing; stronger process/container/network isolation remains a separate
security decision.

==== M0.6 Executable Verification Execution Boundary

M0.6 implements a separate `verification-planning` role with a fresh
`ExecutionAttemptId` and context. Unlike `implementation`, it has no
source/workspace mutation capability. It receives only bounded relevant
repository and patch context and returns structured planning metadata. The
`codex-cli` enforces that boundary with non-interactive ephemeral execution
and `--sandbox read-only`; patch and canonical-source integrity checks before
and after planning detect and reject mutation. Prompt instructions are only
defense in depth, not the source security control.

Planning output is untrusted. Praetor parses it into provenance-bearing
VerificationCandidate values and validates each structured VerificationStep
before execution. Raw AI strings are never interpolated through a shell.
Validation bounds executable and arguments to admitted Core V0 direct-process
templates, resolves tools outside governed source, confines the working
directory to the ProposalWorkspace, applies timeout/cancellation and output
limits, and passes a minimal environment without provider credentials. The
local adapter captures PATH once, admits only absolute existing
non-world-writable directories, excludes proposal/canonical directories from
the child PATH, uses an ephemeral HOME/TMPDIR/build cache, and rejects Go path
settings that target governed source. The authenticated host user's remaining
PATH and installed tools are an explicit V0 trust boundary.
Repository-declared npm/Make scripts remain potentially malicious even when
discovery is deterministic; M0.6 is not hostile-code containment.

Only real Verification Engine execution creates deterministic evidence.
Source/patch linkage and drift checks prevent the planner or tool from
silently changing the artifact being evaluated. Bounded stdout/stderr is
line-redacted for credential markers in runtime evidence. Audit records
presence/truncation and outcome metadata rather than raw process output.

These are minimum V0 controls, not a claim of hostile-code isolation or the
mature M1.0 Policy Engine. Any stronger filesystem, process, container,
network, or credential boundary required by real verification tools must
follow the owning approved milestone's security spike/ADR governance. M1.1
owns recovery and local concurrency; M1.5 owns boundaries required by its
quality/security tools. Neither changes the current worktree boundary by
implication.

==== M0.7 Local Human Decision Boundary

M0.7 has no default, timeout, provider-driven, or session-close approval path.
Only an explicit local interactive command reaches the Approval Port, and only
from `validated` with coherent passing evidence and retained patch/source
linkage. Proposal and canonical integrity are checked before the decision
event and again before the state transition. Because M0.7 performs no
canonical write, the remaining check-to-transition interval grants no patch
application authority.

Rationale is valid UTF-8, single-line, control-free, and limited to 1024 bytes;
shell summary fields are bounded and sanitized against terminal control
injection. Audit stores linkage and bounded rationale, never patch/source
bodies, raw provider/process output, credentials, prompts, or workspace paths.
`local-interactive-human` is provenance only, not authenticated identity.
Decision append and workflow transition are separate append-oriented writes:
failure of the first preserves `validated`, while failure of the second may
leave a truthful attempted decision without a state transition.

==== M0.8 Canonical Application Boundary

Only an exact coherent `APPROVE` HumanDecision permits explicit canonical
application. The retained patch is re-extracted, hashed, surface-checked, and
preflighted against clean canonical HEAD, index, tracked inventory, working
tree, and untracked status. The adapter passes patch bytes on stdin, uses `--`
path separation where paths are arguments, does not persist a patch file, and
does not enable unsafe, reject, three-way, cached, or index application modes.
Post-application proof compares exact diff bytes, paths and digest, checks
reverse applicability, and proves HEAD/index/inventory unchanged. Protected or
unexpected paths cannot bypass the existing ApprovedScope gate.

The in-process adapter lock closes same-process preflight/application races;
external concurrent writers are detected rather than prevented. A detected
late failure is reported with truthful mutation state and no destructive
rollback. Replays fail source-integrity/preflight checks. Audit contains only
bounded linkage and sanitized failures, never raw patch/source, prompts,
credentials, arbitrary environment, provider output, or workspace paths.
`REJECT` uses a non-application closure path and requires canonical source to
remain unchanged.

==== M1.5 External Quality/Security Tool Boundary

Advanced scanners may introduce heavyweight services/images, network and
credential access, supply-chain exposure, licensing constraints, and
different assurance. M1.5 therefore integrates them through replaceable
adapters, prefers approved existing or adequate open-source/local
infrastructure, and never vendors a platform into governed source. A fallback
must expose different assurance; unavailable or inapplicable DAST/scanners do
not become passing evidence. Consequential deployment and final assurance
taxonomy decisions remain milestone-gated.

==== Multi-Tenant Future

If a hosted enterprise control plane is introduced, tenant separation becomes a first-class security requirement. The current local-first design deliberately avoids inventing that deployment before needed.
