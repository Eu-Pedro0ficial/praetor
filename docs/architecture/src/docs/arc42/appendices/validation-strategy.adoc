=== Validation Strategy

Verification is a first-class product capability, not a final “lint step.” The Validation/Verification Engine normalizes heterogeneous tools into evidence understood by workflow/policy.

==== Validation Layers

. **Artifact validation** — schema, required fields, hashes, references.
. **Source-surface validation** — actual diff vs approved expected/possible/protected surface.
. **Syntactic/static validation** — formatting, lint, compile/type check, AST rules.
. **Dependency validation** — dependency graph/manifest/lockfile delta and policy.
. **Test validation** — unit/integration/contract/architecture/mutation as configured.
. **Security validation** — secret/SAST/dependency/container checks as relevant.
. **Compatibility validation** — APIs, schemas, migrations and serialized contracts.
. **Operational validation** — observability/error/performance policies where applicable.
. **Semantic review** — independent AI and human review.

==== Evidence Severity and Gate Semantics

Tools themselves should not decide whether a warning blocks a Change. Adapters normalize findings; Policy Engine maps them to project/organization severity and gate outcome.

==== Test Selection

The system should prefer targeted tests derived from impacted symbols/modules
plus mandatory repository/project suites. AI may assist discovery when
conventions are ambiguous, but AI-selected checks are never themselves proof
and cannot silently replace explicit repository declarations.

==== Regression Analysis

Regression evidence can include:

* previously passing tests now failing;
* changed public contracts;
* unexpected dependency edges;
* unexpected modified modules;
* removed or weakened tests;
* coverage degradation beyond configured policy;
* architecture-boundary violations;
* performance/behavior deltas where baselines exist;
* previously documented regressions relevant to the impacted area.

==== Validation of AI Structured Output

Agent responses requested as structured artifacts are untrusted until parsed and schema-validated. Invalid output causes a failed/retryable execution result, not partially persisted canonical state.

==== Validation of the Runtime Itself

The runtime must test its own governance promises. High-value platform tests include:

* domain state-machine unit/property tests;
* port contract tests;
* adapter conformance tests;
* sandbox boundary tests;
* fixture repositories where agents/tools attempt forbidden writes;
* memory invalidation tests;
* round-trip canonical/projection tests;
* multi-developer Git merge fixtures;
* policy precedence/exception tests;
* provider routing/data-classification tests;
* audit completeness tests;
* deterministic replay of non-LLM workflow stages.

==== M0.3 Executable Source-Surface Validation

M0.3 compares a complete set of actual repository-relative file paths with an
`ApprovedScope`. Paths use `/` as the domain separator. Absolute paths,
Windows drive forms, backslashes, control characters, empty paths, surrounding
whitespace and any `..` segment are rejected. Safe `.` segments, repeated
separators and trailing separators are normalized before category comparison,
so spelling variations cannot bypass a protected path.

Validation applies the following precedence:

. a protected actual path is a violation;
. an expected actual path is accepted and classified as expected;
. a possible actual path is accepted and classified as possible;
. any other normalized path is an unexpected-path violation;
. malformed actual input is an invalid-path violation.

Duplicate normalized actual paths are classified once. If any actual path is
protected, unexpected or invalid, the complete validation result is rejected
while retaining every accepted classification and violation for inspection.
This small result is Change Surface enforcement for M0.3, not the mature
`EvidenceSet` or deterministic build/test verification introduced by M0.6.

==== M0.4 Patch-Surface Validation

M0.4 obtains the actual surface from Git rather than caller-supplied
`--actual` values. The patch adapter uses NUL-delimited Git path output, sorts
the complete changed-path inventory and extracts a binary-capable full-index
patch relative to the approved base revision. Modified, added and deleted
files participate in the same comparison. Rename detection is disabled so the
underlying delete/add paths remain explicit.

The existing M0.3 precedence and typed violations remain authoritative. Every
changed path must be expected or possible. A single protected, unexpected or
invalid path rejects the complete patch without dropping allowed files or
hunks. An empty proposal is also rejected. A successful result is named
`surface-valid` and stays at the Change's `isolated` stage; it does not claim
M0.6 deterministic verification or M0.7 human approval.

Canonical inspection surrounds workspace creation, the narrow controlled
mutation seam, extraction, classification and cleanup. Tests use temporary
Git repositories and prove `HEAD`, index/working-tree status and canonical
file contents remain unchanged, while external drift is reported without
destructive repair.

==== M0.5 Provider Execution Validation

M0.5 places provider execution inside the same canonical-source guard and
ProposalWorkspace lifecycle. The provider adapter cannot supply an arbitrary
writable root or canonical repository path. After provider completion, the
existing Git adapter—not provider output—extracts patch bytes and actual
changed paths, and the existing M0.3/M0.4 ApprovedScope rules remain the sole
surface classifier.

Provider contract tests validate identity and source-state linkage, safe
workspace projection, role requirements, optional provider-scoped models, and
exact selection without fallback. Concrete `codex-cli` tests exercise bounded
version/capability preflight, request shaping, working directory, model
omission/selection, JSONL normalization, bounded output, authentication,
process, unsupported-interface, malformed-output, timeout, cancellation, and
partial-mutation failures through an injected process seam and real fake
executable.

Fixture-repository integration covers expected, possible, protected,
unexpected, mixed forbidden, empty, and partial-failure outcomes. It also
proves canonical `HEAD`, index/working tree, files, tracked inventory and
source digest remain unchanged, no `.praetor` metadata appears, and external
drift fails closed. These checks establish M0.5 provider/patch behavior only;
they are not M0.6 deterministic target-project evidence.

==== M0.6 Planned Verification Discovery and Evidence

M0.6 separates repository discovery, optional AI-assisted planning, structured
plan validation, deterministic execution, and evidence normalization.
Discovery is language/framework/toolchain agnostic: package/dependency
manifests, lockfiles, build/task files, repository scripts, test/lint/typecheck
configuration, CI definitions, toolchain files, and similar project evidence
are examples rather than a closed taxonomy.

Verification knowledge retains its origin: repository-declared,
deterministically inferred, AI-assisted inferred, or user/configured. Explicit
repository declarations generally outrank AI inference. Ambiguity and
conflicts remain visible rather than being converted into invented facts.

The exact AI role `verification-planning` is a new, read-only execution with a
fresh context and `ExecutionAttemptId` distinct from the M0.5
`implementation` attempt. It may inspect bounded source/repository/patch
context and propose structured `VerificationCandidate` values, but it cannot
mutate canonical or proposal source, decide semantic correctness, advance the
Change, approve/reject it, or mint deterministic evidence. Core V0 may reuse
the same explicitly selected provider adapter without introducing routing or
a second provider.

Candidates become a structured `VerificationPlan`. Before execution, every
`VerificationStep` is checked for valid structure and provenance, bounded
executable/argument data, explicit executable resolution, known
working-directory scope, safe environment handling, timeout, cancellation,
and output limits. AI-generated arbitrary shell text is rejected; execution
uses argument vectors without blind shell interpolation. Repository-declared
scripts remain potentially untrusted execution and receive the same boundary
checks.

Only actual Verification Engine tool execution produces deterministic
evidence. A normalized result identifies the step, tool/version where
available, argument vector and bounded working-directory scope, source/patch
linkage, timestamps/duration, exit code, bounded/redacted stdout/stderr or
artifact references, outcome, and only necessary reproducibility environment
metadata. Provider completion, planning confidence, and semantic findings
remain non-deterministic provenance.

The M0.6 gate uses only the minimum deterministic rules required for V0. It
does not implement the mature M1.0 Policy Engine, M1.1 Reviewer, or M1.3/M1.4
routing/multi-provider capabilities. Required passing evidence may authorize
only the existing `isolated -> validated` transition. Human approval remains
M0.7.

==== M1.8 Advanced Quality and Security Evidence Direction

M1.8 broadens replaceable evidence adapters for applicable SAST, SCA, secret,
DAST, IaC, container/image, code-quality, coverage, mutation, architecture and
API/security capabilities. It may normalize approved local, self-hosted,
containerized, managed, existing-enterprise, and CI-provided sources alongside
AI semantic findings.

Evidence must retain source, capability, availability, applicability and
material assurance differences. An approved fallback with lower or different
assurance is not equivalent to the preferred capability; `unavailable` and
`not applicable` are not `pass`. DAST is conditional on an authorized
runnable target/environment. The mature Policy Engine composes deterministic,
external and non-deterministic findings into a Quality Gate without allowing
AI authority to override deterministic tool results.
