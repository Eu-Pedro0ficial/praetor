=== Validation Strategy

Verification is a first-class product capability, not a final “lint step.” The Validation/Verification Engine normalizes heterogeneous tools into evidence understood by workflow/policy.

==== Validation Layers

. **Artifact validation** — schema, required fields, hashes, references.
. **Source-surface validation** — actual diff vs approved expected/possible/protected surface.
. **Syntactic/static validation** — formatting, lint, compile/type check, AST rules.
. **Dependency validation** — dependency graph/manifest/lockfile delta and policy.
. **Test validation** — unit/integration/contract/architecture/mutation as configured.
. **Security validation** — secret/SAST/dependency/container checks as relevant.
. **Compatibility validation** — APIs, schemas, migrations and serialized contracts.
. **Operational validation** — observability/error/performance policies where applicable.
. **Semantic review** — independent AI and human review.

==== Evidence Severity and Gate Semantics

Tools themselves should not decide whether a warning blocks a Change. Adapters normalize findings; Policy Engine maps them to project/organization severity and gate outcome.

==== Test Selection

The system should prefer targeted tests derived from impacted symbols/modules plus mandatory project suites. It must avoid using AI-selected tests as the sole guarantee when organization/project policy requires a known suite.

==== Regression Analysis

Regression evidence can include:

* previously passing tests now failing;
* changed public contracts;
* unexpected dependency edges;
* unexpected modified modules;
* removed or weakened tests;
* coverage degradation beyond configured policy;
* architecture-boundary violations;
* performance/behavior deltas where baselines exist;
* previously documented regressions relevant to the impacted area.

==== Validation of AI Structured Output

Agent responses requested as structured artifacts are untrusted until parsed and schema-validated. Invalid output causes a failed/retryable execution result, not partially persisted canonical state.

==== Validation of the Runtime Itself

The runtime must test its own governance promises. High-value platform tests include:

* domain state-machine unit/property tests;
* port contract tests;
* adapter conformance tests;
* sandbox boundary tests;
* fixture repositories where agents/tools attempt forbidden writes;
* memory invalidation tests;
* round-trip canonical/projection tests;
* multi-developer Git merge fixtures;
* policy precedence/exception tests;
* provider routing/data-classification tests;
* audit completeness tests;
* deterministic replay of non-LLM workflow stages.

==== M0.3 Executable Source-Surface Validation

M0.3 compares a complete set of actual repository-relative file paths with an
`ApprovedScope`. Paths use `/` as the domain separator. Absolute paths,
Windows drive forms, backslashes, control characters, empty paths, surrounding
whitespace and any `..` segment are rejected. Safe `.` segments, repeated
separators and trailing separators are normalized before category comparison,
so spelling variations cannot bypass a protected path.

Validation applies the following precedence:

. a protected actual path is a violation;
. an expected actual path is accepted and classified as expected;
. a possible actual path is accepted and classified as possible;
. any other normalized path is an unexpected-path violation;
. malformed actual input is an invalid-path violation.

Duplicate normalized actual paths are classified once. If any actual path is
protected, unexpected or invalid, the complete validation result is rejected
while retaining every accepted classification and violation for inspection.
This small result is Change Surface enforcement for M0.3, not the mature
`EvidenceSet` or deterministic build/test verification introduced by M0.6.

==== M0.4 Patch-Surface Validation

M0.4 obtains the actual surface from Git rather than caller-supplied
`--actual` values. The patch adapter uses NUL-delimited Git path output, sorts
the complete changed-path inventory and extracts a binary-capable full-index
patch relative to the approved base revision. Modified, added and deleted
files participate in the same comparison. Rename detection is disabled so the
underlying delete/add paths remain explicit.

The existing M0.3 precedence and typed violations remain authoritative. Every
changed path must be expected or possible. A single protected, unexpected or
invalid path rejects the complete patch without dropping allowed files or
hunks. An empty proposal is also rejected. A successful result is named
`surface-valid` and stays at the Change's `isolated` stage; it does not claim
M0.6 deterministic verification or M0.7 human approval.

Canonical inspection surrounds workspace creation, the narrow controlled
mutation seam, extraction, classification and cleanup. Tests use temporary
Git repositories and prove `HEAD`, index/working-tree status and canonical
file contents remain unchanged, while external drift is reported without
destructive repair.
