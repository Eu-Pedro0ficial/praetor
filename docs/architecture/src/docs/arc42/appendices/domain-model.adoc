=== Domain Model

The following model is conceptual and intended to anchor implementation vocabulary. It is not a demand that every concept become a Go struct on day one.

==== Change Aggregate

`Change` is the consistency boundary for a requested software evolution. Its responsibilities include preserving the original intent, current state, selected workflow version, relevant source/memory/policy snapshots, risk and change-surface information, and references to generated artifacts/evidence.

Candidate invariants:

* a Change has exactly one stable `ChangeId`;
* a Change is associated with exactly one registered Project in a single execution context;
* every state transition is attributable to an Actor/System action and a workflow transition;
* an implementation cannot become accepted before all mandatory evidence for the active workflow/policy snapshot is satisfied;
* a FORBIDDEN policy result cannot be overridden by an ordinary approval path;
* an exception must name the policy/constraint being excepted, its authority, reason, scope and optional expiry;
* the source commit used for planning/impact must be identifiable so drift can be detected before application;
* the memory snapshot and policy/workflow versions used to produce an AI Context Pack are identifiable;
* rejected attempts remain part of the Change history.

===== M0.2 Executable Subset

The first executable aggregate contains only `ChangeId`, its single
`ProjectId` association, `ChangeIntent`, current `ChangeState`, creation time
and last-transition time. It exposes state through read-only accessors and
enforces all mutation through the aggregate transition operation.

For M0.2, `ChangeId` is a caller-supplied, non-empty opaque value distinct from
`ProjectId`. This deliberately establishes no generated or public canonical
identifier format. It is not derived from repository location, request text,
time, Git state or mutable workflow state.

`ExecutionAttempt` and the other candidate concepts below are not instantiated
by M0.2 because provider execution, patches, evidence, review, policy and
sandbox behavior begin in later milestones.

===== M0.3 Executable Source Boundary

M0.3 adds a source-state model associated with the existing `ChangeId` and
`ProjectId` without modifying the M0.2 lifecycle state machine.

`SourceSnapshot` contains:

* `ProjectId` association;
* operational `RepositoryRoot` metadata;
* Git `HEAD` revision;
* `clean` or `dirty` working-tree state, including untracked status;
* a sorted, deduplicated inventory of Git-tracked repository-relative paths;
* a versioned `SourceStateDigest` used only to establish snapshot integrity.

`SourceStateDigest` is SHA-256 over length-delimited components: the
`praetor-source-state-v1` label, `HEAD`, porcelain-v1 `-z` status, cached
`ls-files -z` inventory, and the binary full-index tracked diff from `HEAD`.
The status component captures untracked path/status information, but M0.3 does
not read or hash untracked file contents. The digest is not repository
identity, `ProjectId`, or evidence for move, clone, fork, mirror, or
reassociation semantics.

`ImpactAnalysis` takes the Change, SourceSnapshot and a developer authorization
request. Explicit expected and possible candidates are verified against the
tracked inventory; protected paths may name either a tracked file or a tracked
subtree. It performs no AI inference, AST analysis, dependency analysis or
semantic code search.

`ChangeSurface` has an explicit authorization mode:

* `explicit-paths` — exact `expected` paths are strongly expected and exact
  `possible` paths are additionally allowed;
* `repository-wide` — every normalized repository-relative path is allowed as
  a discovered `possible` change unless a protected constraint matches it.

`protected` paths are forbidden in both modes and protect both the named path
and its descendants. Inputs are canonicalized with deterministic precedence:
`protected` over `expected` over `possible`, followed by the repository-wide
fallback. `ApprovedScope` is the M0.3 repository write boundary used for
validation; it is not a mature M0.7 human approval decision.

The CLI token `.` selects repository-wide mode but is not stored as an
`expected` or `possible` path. Absolute paths, traversal and malformed paths
remain invalid. The Git worktree and normalized repository-relative patch paths
bound repository-wide authority. Symbol scope remains represented in the
longer-term conceptual model below but is not claimed or enforced by the
current runtime.

===== M0.4 Executable Proposal Boundary

M0.4 adds a process-local `ProposalWorkspace`, `PatchArtifact`, `Proposal` and
`CanonicalSourceGuard` without changing the authoritative M0.2 Change state
machine. A proposal workspace links a random `WorkspaceId`, `ProjectId`,
`ChangeId`, canonical repository association, external worktree path, exact
base revision and M0.3 `SourceStateDigest`. `ChangeId` is linkage only and does
not control filesystem placement.

The small workspace lifecycle is operational rather than a competing Change
lifecycle: `active` may become `retained`, `rejected`, `failed`,
`cleanup-failed`, or `cleaned`; retained, rejected, and failed workspaces may
later become `cleanup-failed` or `cleaned`. A surface-valid patch is retained
with the Change still `isolated`. It is neither M0.6 `validated` nor M0.7
`approved`. A protected, unexpected, invalid, or empty patch is rejected as a
whole and retained until explicit discard or retry cleanup. A provider or
post-provider extraction failure marks the workspace failed because partial
mutation may exist. Cleanup failure remains explicit and blocks reuse.

`PatchArtifact` retains the proposal linkage, base revision, source-state
relationship, binary-capable Git patch bytes, sorted changed paths, a compact
diff summary, SHA-256 patch digest and creation time. Full patch bodies are not
written to the M0.4 audit metadata. No new canonical persistent artifact
format is selected.

`CanonicalSourceGuard` reuses deterministic M0.3 inspection before and after
proposal stages. Dirty canonical source fails closed. External drift is
reported and preserved; Praetor does not stash, reset, clean or repair the
developer's repository.

The executable append-oriented event set is
`PROPOSAL_WORKSPACE_CREATED`, `PATCH_EXTRACTED`,
`PATCH_SURFACE_VALIDATED`, `PATCH_REJECTED`,
`PROPOSAL_WORKSPACE_FAILED`, `PROPOSAL_WORKSPACE_CLEANUP_FAILED`, and
`PROPOSAL_WORKSPACE_DISCARDED`. Events link `ProjectId`, `ChangeId`, random
workspace identity, base revision, source-state digest, disposition and, when
present, patch digest, diff summary, changed paths and surface violations.
They deliberately omit full patch bodies and temporary workspace paths.

===== M0.5 Executable Provider Boundary

M0.5 introduces a provider-independent AI Provider Port on the
application/core side without modifying the authoritative Change state
machine. The port is expressed in Praetor vocabulary:

* `ProviderCapability` is descriptive adapter contract metadata. It is not a
  routing score or policy;
* `ProviderRoleContract` names only the M0.5 `implementation` role and
  its required capabilities;
* `ExecutionRequest` links a random Praetor-owned `ExecutionAttemptId`,
  `ProjectId`, `ChangeId`, intent, ApprovedScope, base/source state, explicit
  provider/model selection, and a safe `ProposalWorkspace` projection;
* `ProviderResponse` normalizes provider version when safely available,
  external execution identity, selected provider/model, completion, bounded
  textual summary, optional usage, and timestamps. It is provenance, not
  source authority.

The safe workspace projection omits canonical `RepositoryRoot`; the adapter
receives only the isolated writable workspace. Git remains authoritative for
patch bytes and actual changed paths. A completed provider call therefore
flows into the existing M0.4 patch extraction and surface comparison. A valid
result retains the proposal and leaves the Change `isolated`; provider
completion does not mean M0.6 validation or M0.7 approval.

The first adapter is `codex-cli` under ADR-030, with structured vendor metadata
`OpenAI`. Adapter, vendor, model, `implementation` role, and attempt identity
remain distinct. Provider and optional provider-scoped model selection are
session/runtime metadata and are not part of Change identity or the port's
hard-coded defaults. Process-local `SelectionProvenance` distinguishes the
built-in default, environment, composition configuration, session command, and
provider default without introducing persistent provider configuration.

`LocalReadiness` is provider-independent, bounded evidence with a disposition
of `locally-available`, `locally-ready`, `unavailable`, `misconfigured`,
`unsupported`, or `indeterminate`. It describes local setup only.
Authentication remains `not-verified`; executable discovery does not prove
credentials, network reachability, or model availability. A proven blocking
readiness disposition returns a typed pre-invocation error before an
`ExecutionAttemptId` or provider lifecycle event exists. `ExecutionAttemptId`
is Praetor-owned; a Codex thread identifier is optional external provenance.

The append-oriented M0.5 event set is `PROVIDER_EXECUTION_STARTED`,
`PROVIDER_EXECUTION_COMPLETED`, and `PROVIDER_EXECUTION_FAILED`. Events link
the attempt, Project, Change, workspace, provider/model, role, base/source
state, timestamps, disposition and bounded success/failure metadata. Patch
events produced by an execution also link the Praetor attempt identity. Raw
prompts, source bodies, provider output, workspace paths, and credentials are
not audit metadata.

Each invoked implementation attempt owns a distinct `ExecutionAttemptId`.
Failure keeps the Change `isolated` and makes workspace disposition explicit.
A retry removes the prior failed/rejected workspace before creating a new
random workspace at the original base and source digest. It appends a new
source-snapshot binding scoped by WorkspaceId while retaining prior artifacts
and events. Canonical drift blocks replacement creation; no old proposal can
be applied through retry.

===== M0.6 Executable Verification Boundary

M0.6 extends the provider-independent role contract with the exact
`verification-planning` role while preserving `implementation` as a separate
responsibility. A planning invocation has its own Praetor
`ExecutionAttemptId`, role identity, provider-scoped model selection, and
fresh execution context. It does not inherit an implementation scratchpad or
hidden provider conversation. The same `codex-cli` adapter may serve both
roles in Core V0, but each invocation remains a distinct attempt; this does
not constitute automatic routing or mature multi-provider operation.

Verification planning receives only bounded read context derived from the
SourceSnapshot, Repository Context, ChangeIntent, ApprovedScope, and
PatchArtifact. It has no source/workspace mutation capability and cannot
advance, approve, or reject the Change. Its output is planning provenance, not
deterministic or semantic-correctness evidence.

`VerificationCandidate` identifies a proposed deterministic check and retains
its origin, supporting repository evidence, and AI inference metadata when
present. Origins such as repository-declared, deterministically inferred,
AI-assisted inferred, and user/configured remain distinguishable; explicit
repository declarations generally outrank AI inference.

`VerificationPlan` is a validated collection of structured
`VerificationStep` values. A step conceptually carries a kind, executable/tool
identity, argument vector, bounded working-directory scope, origin, and
supporting evidence. These concepts do not select a canonical persistent
serialization. Arbitrary AI-produced shell text is not a VerificationStep and
must not become executable authority.

Only the Verification Engine's actual structured tool execution produces
deterministic `EvidenceSet` items. Evidence links the source and patch,
verification step, tool/version where available, arguments and bounded
working-directory scope, timestamps/duration, exit code, bounded/redacted
output or artifact references, outcome, and only necessary reproducibility
metadata. AI planning and later semantic review remain separate
non-deterministic provenance. Required successful evidence permits only the
existing `isolated -> validated` Change transition.

===== M0.7 Human Decision Boundary

M0.7 introduces an immutable process-local `HumanDecision` with exactly two
decision kinds: `APPROVE` and `REJECT`. Absence of a decision is absence of
authorization. The value links Project, Change, retained proposal workspace,
base revision, source-state digest, patch digest, verification attempt,
EvidenceSet, decision timestamp, requested disposition, changed-path/evidence
counts, the optional bounded rationale, and actor provenance.

The actor provenance is exactly `local-interactive-human`. It truthfully means
that the command entered through the local interactive process; it is not an
authenticated operating-system, enterprise, or personal identity. Rationale
is optional, trimmed, valid UTF-8, single-line, control-free, and limited to
1024 bytes.

A HumanDecision can be created only for a `validated` Change with a retained
PatchArtifact, coherent passing deterministic evidence, and unchanged
proposal/canonical integrity. `APPROVE` requests `approved`; `REJECT` requests
`rejected`. M0.7 does not apply the patch or automatically advance either
disposition. M0.8 introduces a bounded canonical application Result linked to
the same Project, Change, workspace, base/source/patch digests,
VerificationAttempt, EvidenceSet, and HumanDecision. An approved Result proves
the exact canonical diff and changed paths, unchanged HEAD/index, a changed
dirty SourceSnapshot digest, and completion time/result digest before
`audit-locked`. Rejected closure has no application Result and instead proves
canonical source unchanged. Both terminal paths then clean the session-owned
workspace.

===== M1.1 Durable Authority

ADR-033 preserves the existing state machine and identifies a durable Change
by `(ProjectId, ChangeId)`, with opaque project-scoped ChangeId. Recovery
conditions are not Change states.

An M1.1 `Artifact` has an opaque generated ArtifactId independent from its
ContentDigest and belongs to exactly one Project and Change. Its versioned
envelope/payload and parent/dependency relations are immutable. A modification
creates another Artifact; supersession is append-only; and a committed Change
revision advances exact role bindings. Existence, integrity, schema validity,
binding, disposition, freshness, supersession, and availability remain
separate dimensions. Specification/ChangePlan authority semantics remain M1.3.

`WorkflowSnapshot` authority contains WorkflowId, WorkflowVersion,
WorkflowDigest, workflow schema version, and exact embedded Core V0 YAML bytes.
The digest is SHA-256 over exact bytes. Parsed workflow models are derived;
same identity/version with a different digest conflicts; unsupported old schema
remains inspectable and cannot advance. There is no automatic in-flight
workflow migration.

`ExpectedRevision` guards each durable Change successor. Consequential work
uses a Project-unique opaque OperationId bound to immutable RequestDigest and,
for Change operations, ChangeId. Orthogonal recovery conditions describe
incomplete/uncertain effects, source divergence, corruption, or incompatibility
without altering ChangeState. The one per-Project SQLite adapter supplies
logical ChangeStore, ArtifactStore, and AuditLedger responsibilities plus a
typed all-or-none authority commit.

===== M1.2 Implemented Repository Intelligence Model

ADR-039 defines `RepositoryModel` as an immutable Project-scoped description
of one exact source/build condition. It belongs to the Project rather than one
Change and is identified by a schema plus a build key over SourceFingerprint,
analyzer set, and analysis configuration. Its bounded graph contains
Repository, Module, File, Symbol, Test, API, ExternalDependency, Owner,
ArchitectureElement, and UnresolvedReference nodes with explicit containment,
declaration, dependency, reference, test, exposure, ownership, architecture,
and inferred co-change relationships.

Each repository assertion is OBSERVED, DERIVED, or INFERRED with bounded
evidence provenance. Confidence HIGH/MEDIUM/LOW exists only for INFERRED
assertions. `KnowledgeGap` identifies the affected scope, reason, evidence,
consequence, and possible resolution; missing or excluded knowledge is never
converted into a negative fact.

`SourceFingerprint` composes M0.3 source state, exact HEAD/working condition,
tracked path/mode/content, symlink link text, Gitlinks, and sorted untracked
status-name evidence. Untracked bytes are excluded from analysis. Untracked
create/delete/rename changes the comparable fingerprint; byte-only edits to an
already-known excluded untracked file do not. Exclusion always produces a gap.
Freshness is CURRENT, STALE, or UNKNOWN and is checked again at use time.

ADR-040 defines `ImpactReport` as an immutable Change-owned Artifact over an
exact intent and RepositoryModel. It contains expected, possible, protected,
and uncertain impact with explanation paths, gaps, limits, and an advisory
RiskProfile. The ordered risk categories are LOW < MODERATE < HIGH;
INDETERMINATE is outside the ordering and means evidence is insufficient.
Impact and risk cannot expand `ApprovedScope`, authorize a write, or establish
policy/approval authority. Historical reports remain inspectable, while
current use requires current model inputs.

The production implementation is in `internal/repositorymodel`,
`internal/repository`, `internal/adapters/repositoryanalysis`,
`internal/adapters/persistence/modelcache`, and `internal/impact`. It uses the
existing M1.1 artifact authority for durable reports and is exposed through the
existing hierarchical command registry. M1.2 awaits independent closure audit.

`SpecificationPack` is target architecture only. M1.3 must decide its schema,
version, identity, authority, approval, invalidation, and relationship to
`ChangePlan`. The planned `engineering/specs/` path is a candidate
governed-source location rather than an existing directory or accepted
canonical format. The required future trace is requirement -> spec -> change
-> evidence -> policy; it must not duplicate or replace the authoritative
requirements catalog or traceability ledger.

==== Project Aggregate / Registry

A registered Project provides stable association among a logical project identity, the source repository association, memory repository association and local tool configuration. The registry should not require application source code modification merely to establish this link.

The logical Project is distinct from repository location, checkout, worktree, Git remote, and source revision. ProjectId is an opaque generated identifier, while RepositoryRoot is operational association metadata and not identity. The durable local registry lives outside the repository and remains local-user application data.

Potential fields include project identifier, repository root, schema version, creation timestamp, and future association metadata only when a concrete requirement justifies it. A repository fingerprint is intentionally deferred and is not part of the initial C02 metadata contract.

==== Agent Role Model

A Role describes responsibility and required capabilities. A Provider supplies capabilities. A RoutingPolicy decides whether a Provider may fulfill a Role for a particular data classification and execution.

This prevents domain terminology such as `ClaudePlanner` or `CodexImplementer` from becoming architectural dependencies.

==== Evidence Model

Evidence should be typed. Candidate evidence types include:

* SourceDiffEvidence
* ChangeSurfaceEvidence
* CompilationEvidence
* TypeCheckEvidence
* StaticAnalysisEvidence
* UnitTestEvidence
* IntegrationTestEvidence
* ContractTestEvidence
* ArchitectureTestEvidence
* CoverageEvidence
* MutationTestEvidence
* SecurityScanEvidence
* SecretScanEvidence
* DependencyScanEvidence
* PerformanceEvidence
* AIReviewEvidence
* HumanReviewEvidence
* ApprovalEvidence

Each item should identify producer/tool, version where possible, input
snapshot and patch, verification origin, execution timestamp, normalized
result and artifact/hash references. Deterministic tool results, external
evidence, AI planning/semantic findings, and human decisions retain distinct
evidence authority.

==== Memory Aggregate

Canonical memory is not one mutable “memory object.” It is a collection/stream of typed records and lifecycle events. The Memory Engine derives the currently active knowledge view from canonical history.

The separation between a record's *statement* and its *status* is important. A record can remain historically true (“the system used RabbitMQ before migration X”) while no longer being an active description of current architecture.

==== Policy Model

Policy is a governance rule, not merely instructions appended to an LLM prompt. A Policy may have deterministic checks, advisory semantic checks, applicability selectors, severity, enforcement disposition, evidence requirements, authority requirements and exception rules.

The M1.0 executable model includes immutable `Policy`, `PolicyBundle`,
individual `PolicyDecision`, conjunctive `AggregateRequirements`, and
`PolicyExceptionCandidate`. A bundle decision retains exact evidence and
manifest-digest linkage. It neither changes `ChangeState` nor grants an
exception.
