=== Configuration and Precedence Model

Configuration is explicit and ordered by precedence. The authoritative model is:

built-in defaults < user configuration < project configuration < workflow configuration < Change-specific configuration

Governance authority is not subordinate to configuration precedence. A lower-level configuration cannot weaken a higher-authority non-overridable policy.

Example: if organization governance forbids an external provider, project or Change configuration cannot re-enable it.

==== Required Distinction

The system must distinguish between:

* CONFIGURATION PRECEDENCE — which value wins when multiple layers define the same setting;
* GOVERNANCE AUTHORITY — which source is allowed to override a mandatory rule or deny an operation.

Configuration precedence explains the effective value. Governance authority explains whether a value is allowed to be effective at all.

M1.0 enforces this distinction when composing policy bundles: later
configuration may replace an overridable policy, while an attempted change to
a non-overridable authoritative policy fails closed. Organization inheritance
is not implemented.

Provider credentials are not normal project configuration and must not be stored in canonical memory/source configuration.

==== M0.5 Runtime Provider Selection

M0.5 implements a narrow process-runtime bridge while the mature layered
configuration system remains future work. `PRAETOR_AI_PROVIDER` selects an
exact compile-time registered adapter and defaults to `codex-cli`.
`PRAETOR_AI_MODEL` optionally selects a provider-scoped model; absence means
the provider default. The interactive `provider select <provider>` and
`provider model <model>` commands may replace these values for the active
session without recompilation or persistent Project configuration.

Unknown providers fail; selection does not route, rank, fall back, retry on a
different provider, or override governance. Effective selection retains
process-local provenance: built-in default, environment, composition
configuration, session command, or provider default as applicable. Selecting a
new provider clears the previous provider-scoped model; selecting a model
changes only the active session. Restart restores the environment/built-in
selection because interactive selection is intentionally not persistent.

The startup configuration audit records only provider identity and model
identity or `provider-default`. Read-only `provider diagnose` is not audited and
does not create an execution attempt. Codex CLI authentication remains outside
these values and is not copied into Praetor configuration or audit.

==== M0.9 Presentation Preferences

Presentation preferences are distinct from the governed configuration model
above. They are user-local, affect rendering only, and never participate in
configuration precedence or governance authority. The narrow versioned JSON
document is stored under the platform user configuration directory at
`praetor/presentation-v1.json` (`$XDG_CONFIG_HOME` on Linux when set), outside
governed repositories.

The document contains only sidebar/section visibility and colors selected from
a bounded Praetor-owned vocabulary; identical explicit foreground/background
choices are rejected to preserve readable regions. Missing files use defaults. Reads reject
unknown fields, malformed or oversized content, symlinks, and unsafe file
permissions. Writes use a process-coordinated lock, a private temporary file,
file synchronization, atomic replacement, and directory synchronization.
Invalid updates do not partially replace either persisted or process-local
preferences. The document contains no credentials, project state, evidence,
policy, audit data, or provider configuration.

==== Configuration Drift

The runtime should be able to show the effective configuration for a Change, including source of each rule. This is analogous to a compiler explaining effective flags and is important when organization/project policies overlap.

==== M1.2 Analysis Configuration and Storage Separation

Analysis configuration that can change a RepositoryModel result participates
in the exact analysis-configuration digest and therefore in the model build
key. Analyzer identity/version/capability participates in the analyzer-set
digest. A configuration change cannot reuse a model produced under a different
key or reinterpret an existing immutable ImpactReport.

M1.2 uses a per-Project SQLite performance cache beneath the platform cache
directory (`$XDG_CACHE_HOME/praetor/projects/<validated ProjectId>/` on Linux,
with the platform fallback when unset). It is distinct from CONFIG, the M1.1
authoritative SQLite database under XDG DATA, short locks under XDG STATE, and
governed source. Cache path configuration cannot redirect runtime metadata into
the governed repository. Missing, corrupt, incompatible, or deleted cache data
is rebuilt and never treated as authoritative loss.
